# Phase 5 - inspector fine-tuning, round 2

## Overview

A second, smaller fine-tune pass over the inspector, continuing
[`04_fine_tunes.md`](04_fine_tunes.md). Two items surfaced once phase 4's new
`stage=mission` llm_call made a gap visible and once real logs showed the move
round-trip noise. Both are grounded against the code below. Context:
[`00-start.md`](00-start.md); catalogue in
[`01_struct_log_analysis.md`](01_struct_log_analysis.md); TUI in
[`02_textual_tui.md`](02_textual_tui.md).

## Original draft notes

- Orphan llm calls: there is a `stage=mission` llm_call now, but the mission
  itself is never printed to the TUI.
- Repeated `world_request`/`world_response` pairs: mostly the move req/res
  success pattern, ~10 lines of noise for a few steps. `alog` already has
  machinery to collapse repeated lines with an `xN` suffix.

## Findings (grounded in code)

1. **The generated mission never reaches the log.**
   `Player.play` (`player.py:190`) calls `_generate_mission_objective()` -
   which emits `llm_call stage=mission` - then immediately
   `_start_new_mission(new_obj)` (`player.py:191`) in the same turn.
   `_start_new_mission` (`player.py:238`) builds the new `Mission` but only
   `alg.log`s it; it emits no struct-log event. So the `.jsonl` shows a
   `stage=mission` llm_call with no companion event carrying the objective -
   an orphan. The existing `mission_transition` event
   (`player.py:231`) is unrelated: it fires only on build/craft responses and
   carries `to_status`, never an objective.
2. **Consecutive identical round-trip rows are pure noise.** After phase 4,
   one move round trip renders as a single `WRecMove -> WResMove
   status=success` line. A move of distance N validates each step, so a turn
   emits N such identical lines back to back. `alog` (`src/laife/ui/alog.py`)
   already handles this for the console: it tracks `last_msg`/`dup_count` and
   rewrites one line as `... (xN)` for immediately-consecutive duplicates
   (not a global dedup - only runs). The TUI has no equivalent; it shows every
   repeat.

## Goals

1. **Surface the mission (close the orphan).** Emit a new struct-log event
   from `_start_new_mission` carrying the objective, so the TUI shows what the
   `stage=mission` llm_call produced.
   - New constant `EVT_MISSION_START = "mission_start"` in
     `log_events.py`. Bind `player, turn, objective` (and
     `from_status`=the ended mission's status, for context). Emit it in
     `_start_new_mission` next to the existing `alg.log`.
   - TUI: add `mission_start` to `EVENT_COLORS` and a detail builder
     (`objective=...`). It correlates with the orphan llm_call by
     `(player, turn)`, so focus-turn now shows
     `llm_call(stage=mission) -> mission_start` together.
   - Decision: a dedicated event, not an extra field on `mission_transition`
     or on the llm_call. `mission_transition` means "status changed on a
     build/craft response"; overloading it blurs the phase-1 catalogue. The
     objective is not known until after the llm_call returns, so it cannot
     ride on that event either.
2. **Collapse consecutive identical rows with an `xN` suffix.** Mirror
   `alog`'s run-collapse in the TUI, applied to displayed rows *after* the
   phase-4 request/response pairing.
   - Signature = `(player, event, detail-text)`. Player is in the signature so
     two players' interleaved moves never merge; only a true consecutive run
     collapses (matching `alog`, not a global dedup).
   - When a new row's signature equals the previous displayed row's, increment
     a count and rewrite that row's detail cell to end with ` (xN)` instead of
     adding a row; otherwise append and reset the run.
   - Disabled under turn focus, same rule as the pair-collapse: focus wants the
     full, uncollapsed chain. Reset the run state in `_rerender_table`.

## Design notes and risks

- **Interaction with phase-4 pair-collapse (the main risk).** A
  `world_request` is displayed immediately (signature `WRecMove`), then
  upgraded in place to `WRecMove -> WResMove status=success` when the response
  lands (`_collapse_response`). Its final signature is only known *after* the
  upgrade, so the run-collapse comparison must run at two points: on plain
  append, and again right after `_collapse_response` mutates a row. Factor a
  single `_merge_if_repeat(index)` helper that compares the row at `index`
  against its predecessor and, on a match, folds it in (drop the row or mark
  it counted) - called from both the append path and the upgrade path so the
  logic lives in one place.
- **Row-count bookkeeping.** Folding a row after it was already added means
  removing it from the `DataTable` and from `_displayed_rows`, which shifts
  indices used by `_pending_round_trips`. Two clean ways to avoid index drift:
  (a) do the repeat check *before* physically adding the row (decide append
  vs. merge up front) for the plain path, and for the upgrade path re-derive
  pending indices; or (b) keep a parallel display-model list and rebuild.
  Prefer (a); the upgrade path only ever merges the just-upgraded last-or-near
  row, so pending-index fixup is local. Spell this out in code, it is the
  fiddly part.
- If (a) proves too tangled with `_pending_round_trips`, fall back to a pure
  `_recompute_display()` that filters -> pairs -> run-collapses the raw rows
  and rebuilds the table. Simpler and obviously correct; the cost is an O(n)
  rebuild per event, acceptable for a dev inspector but a change from the
  current incremental append. Decide during implementation; note which was
  taken in the outcome.

## Out of scope

- Global (non-consecutive) dedup, e.g. folding the once-per-turn `observe`
  round trip that is not consecutive. Run-collapse only, matching `alog`.
- The startup/shutdown warnings ([`05_random_warnings.md`](05_random_warnings.md)) -
  still a separate future cleanup.
- Any new filters or bindings; no new columns.

## Outcome

Done, both goals, verified end-to-end against a real game log.

- Goal 1 (mission visibility): new `EVT_MISSION_START = "mission_start"`
  emitted from `_start_new_mission` with `player, turn, from_status,
  objective`; TUI colors it `bright_magenta` and shows `objective=...`.
  Real-log check: `mission_start` count equals the `stage=mission` llm_call
  count (2 == 2) - the orphan is now paired, and focus-turn shows
  `llm_call(stage=mission) -> mission_start` together.
- Goal 2 (run-collapse): implemented via the plan's fallback - a pure
  `_build_display()` (filter -> pair-collapse -> run-collapse) plus a single
  `_refresh()` that rebuilds the table. This replaced phase 4's incremental
  in-place upgrade + `_pending_round_trips` bookkeeping rather than layering
  the fragile index fixup the risk section warned about; the incremental
  machinery (`_show_row`/`_collapse_response`/`_append_table_row`/
  `_rerender_table`) is gone. Consecutive identical entries fold via
  `_signature = (player, event, detail)` into one `(xN)` row; disabled under
  turn focus. To keep the initial load O(n) despite per-event rebuilds, the
  UI worker now drains the queue in batches (one `_refresh` per batch).
  Real-log check: 1379 raw rows -> 246 displayed, move bursts collapsing to
  `(x10)`; phase-4 pair-collapse and all filter/focus tests still pass
  unchanged.
- Extra polish found via the real-log check: event-less startup lines
  (`Loading Laife params`, env info - logged without an `event=` bind) were
  rendering blank, which the run-collapse then surfaced as a bare `(x3)`.
  `_detail` now falls back to the row's `message` when there is no event and
  no extras, so they read sensibly.
- Tests: `mission_start` emission in `test_player_lifecycle.py`; and in
  `test_tui.py` the `xN` collapse, run-break, interleaved-player no-merge,
  focus-shows-uncollapsed, mission_start render, and message fallback. 7 new
  tests. Full suite green: 220 passed, ruff and pyright clean.
